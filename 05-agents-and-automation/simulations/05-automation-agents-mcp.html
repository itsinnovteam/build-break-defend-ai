MCP: one standard plug for tools

Once you have tools, you need a tidy way to connect a model to them - ideally the same way every time, so a tool built once works with any agent. MCP (Model Context Protocol) is that standard. A small server offers a set of tools; a client (your agent) asks what's on offer and calls them. They talk in plain JSON messages.

Analogy - USB-C. Before USB-C, every device had its own charger. Now one shape fits everything. MCP is the USB-C of tools: a tool that speaks MCP plugs into any agent that speaks MCP, with no custom wiring.
Analogy - the waiter and the kitchen. You never shout orders straight into the kitchen. A waiter takes your order to a kitchen that only serves what's on the menu. The MCP server is that waiter: it decides which dishes (tools) exist, and the kitchen behind it stays out of reach.
SOC: a "SOC tools" MCP server exposes get_alert, search_logs, lookup_ip_reputation - read-only. DevOps: a "cluster" server exposes get_pod_status and list_deploys, but not delete_pod. What a server leaves out is a security decision.

Least privilege at the server

The Lab 5 server exposes only four read-only tools. The dangerous ones (disable_account, send_email, block_ip) are not reachable through MCP at all. Even a fully tricked model cannot call what the server never put on the menu. This is the same "least privilege" idea as Module 1's safety rules and Module 4's data access - applied to tools.
